# FSM Editor

VS Code extension (desktop and web: vscode.dev, github.dev): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, "The .fsm file format", its schema and test cases); the layout file's is fsm-editor-common's (its `schemas/fsm-layout.schema.json` and `tests/fixtures/layout`; described for users in `docs/UML-CONFORMANCE.md`, "The layout file"). Reading and writing both files, converting old files, validation, the grammar's checks, comparing, merging and code generation are fsm-editor-common's (`../fsm-editor-common`, Rust), run as WebAssembly: this extension keeps the UI, the diagram's geometry and editing, and VS Code's integration. Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when saved.

## Commands

```sh
npm install
npm run build:common       # fsm-editor-common (../fsm-editor-common) as WebAssembly, with fsm-cli's templates (../fsm-cli), the schemas and the interface's cases, into common/ (needs Rust + wasm32-unknown-unknown)
npm run compile            # tsc type-check (noEmit), then esbuild bundles
npm run watch              # esbuild watch
npm run test:unit          # unit and code generation tests (node:test, bundled by test/unit/run.mjs)
npm run test:web           # browser smoke test in VS Code for the Web (Chromium, headless)
npm run check:webview      # syntax-check media/editor.js
npm run package            # builds fsm-editor-<version>.vsix (vsce package --no-dependencies; release.yml runs it too)
```

`common/` (`common.wasm`, `templates/ts.jinja`, `templates/sml.jinja`, `schemas/*.schema.json`, `api-cases/`) is git-ignored: the extension, the text view's schemas, the tests and the VSIX need it (`api-cases/` isn't packaged). Run `npm run build:common` once, and again after changing `../fsm-editor-common` or `../fsm-cli`; it finds `cargo` on the PATH or in `~/.cargo/bin`. The workflows download it from the fsm-editor-common release pinned by `FSM_COMMON_VERSION` in `release.yml` (`test-windows.yml` reads the pin from there), so that release must exist before this extension is released.

F5 launches an Extension Development Host on `examples/`. Automated tests:
- `npm run test:unit` (`test/unit/common.test.ts`): the client (`src/common.ts`) replays fsm-editor-common's interface cases (`common/api-cases`) and writes the examples back unchanged.
- `npm run test:unit` (`test/unit/codegen.test.ts`): generates TypeScript through `common/common.wasm` with `ts.jinja` for the examples and for models built in code (`ModelBuilder` in `harness.ts`), bundles it with esbuild and runs it against recorded actions and a fake clock. Code model assertions go through a template that prints the code model as JSON (`codeModel()` in `harness.ts`). Add a case here for any change to code generation semantics (made in `../fsm-cli`).
- `npm run test:unit` (`test/unit/sml.test.ts`): generates C++ with `sml.jinja` for the examples and for a model of every feature, compiles it (`-Wall -Wextra -Wpedantic -Werror`) with a driver that records the calls (`cpp.ts`), and runs the same scenarios as the TypeScript tests. Needs a C++17 compiler (`CXX`, or `c++`/`clang++`/`g++`) and Boost.SML: `SML_INCLUDE`, or downloaded once into `node_modules/.cache`; skipped without them, but failed when `CI` is set (GitHub Actions sets it). CI compiles it with GCC, so check GCC too when changing the template (e.g. in a `gcc` container).
- The format, conversion, validation, the grammar, comparing and merging are tested in fsm-editor-common (`cargo test` there, and the umbrella's `node parity/check.mjs`).
- `npm run test:web` (`test/web/index.ts`): opens copies of the examples in VS Code for the Web and checks activation, validation diagnostics at their lines, following a text edit, its save and its text closed unsaved, submachine resolution, opening an old or conflicted file unchanged and converting an old file on save, code generation, the diagram diff and merge, a layout file renamed with its model file, and untitled machines.

Otherwise verify changes in the development host with the examples (`MediaPlayer.fsm`, and `Order.fsm`, which uses `Payment.fsm` as a submachine).

## Architecture

- Build: `esbuild.mjs` bundles `src/extension.ts` twice, into `out/extension.js` (Node, `main`) and `out/web/extension.js` (web worker, `browser`). Extension code must stay web-compatible: no Node modules, `Buffer` or `process`. Use `src/util.ts` for paths and text encoding, and `vscode.workspace.fs` for files. Only `src/trace/tail.ts` may use Node modules; the web build replaces it with `tail.web.ts` (esbuild plugin in `esbuild.mjs`).
- `src/extension.ts`: activation and commands (new machine, generate code, SVG and PNG export, open as text / as diagram, compare as diagrams). `activate` returns `sessionSummary()` for the browser test.
- `src/common.ts`: the client of fsm-editor-common's module (`common/common.wasm`), compiled once at activation (`initCommon`; synchronously, which Node and the web extension host's worker allow) and called synchronously: one JSON request per call (its `schemas/api.schema.json`). It reads and writes the two files (`readMachine`, `writeMachine`, which gives generated names and resolves references, `LostError` for what the format can't hold), loads a model from either format (`load`), converts old files (`convertGroup`), validates, checks a field's text (`checkText`), compares (`compareModels`, with the changes' descriptions; `keysOf`), splits conflict markers, takes a side (`adopt`), gives the derived ids, and generates code. A trap gets a new instance at the next call.
- Code generation (documented in `docs/CODEGEN.md`) is fsm-cli's (validation, code model, Jinja templates), in fsm-editor-common's module: the texts of the `.fsm` files and of the template in, the files to write and the problems (`issues`, `error`) out, as fsm-cli's README ("WebAssembly") describes. The module reads no files: `src/codegenCommand.ts` reads the machine and the machines its submachine states reference, transitively (an open document's text when it is open), keyed by `/`-separated paths, then writes the files through `vscode.workspace.fs`. Templates are `.jinja` only; the module refuses `.hbs` with its own message, which the command shows as it is. The code model, the template language and the bundled templates are fsm-cli's.
- `src/fsmEditorProvider.ts`: `CustomEditorProvider` with its own document (`FsmDocument`), because one diagram edits two files: a document state holds the texts of the model and layout files and the webview's model JSON; each webview `edit` (model JSON) is written by fsm-editor-common (`stateOfModel`) into a new state, fired as an undoable edit (VS Code's undo, redo, dirty mark, save, revert and hot-exit backups act on these states). An edit the format can't hold (`lost`) is refused. Saving writes both files (a layout file that couldn't be read is replaced only after asking); saving an old file converts the files linked to it too (`convertLinked`). Without changes of its own, a document follows its files on disk and the model file's text document. Read-only file systems (Git's) give a read-only diagram. The provider also lists the workspace's machines, resolves submachine paths, maps the Trace Player's ids to the diagram's (`derivedIds`), and publishes diagnostics at the lines the writer or reader gives.
- `src/model.ts`: `FsmModel`, a flat vertex list where `parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. Coordinates are absolute.
- A reference that names nothing is kept as `UNRESOLVED` + its text (`src/common.ts`).
- `src/sessions.ts` links diagram panes, with fsm-editor-common's comparison and `adopt`: `DiffSession` (two panes, from **Compare as Diagrams**, since VS Code opens diffs of `.fsm` files as text diffs; nothing else is paired, so the sides are always known), `MergeSession` (the conflicted document as the result, its two sides served read-only by the `fsm-merge` file system, Git's common version through the Git extension when it is there). The webview shows a pane's role, marks and list (`diff` message) and sends `view`, `diffNav`, `diffLayout`, `mergeChoose`, `mergeAll`, `mergeComplete`.
- `media/editor.js` / `editor.css`: the whole diagram editor (toolbox, SVG canvas, properties panel, inline editing, SVG and PNG export). It's plain JavaScript without a build step or dependencies, and renders by rebuilding an SVG string. Its `cleanGroups` repeats `normalizeGroups` of `src/model.ts`, which the webview can't import. Its geometry is also ported to `Geometry.cs` (`../fsm-editor-vs`) and `Geometry.kt` (`../fsm-editor-jb`). Names ending with `*` are generated and not shown (`shown()`); name fields refuse spaces, `*` and `.` and names used elsewhere in the machine. The grammar's checks of fields and labels (behaviors, conditions, triggers, events, stereotypes) are requests to the extension host (`checkText` message, answered with fsm-editor-common's `checkText`), made when a field or label is committed: on Enter the box waits for the answer, and stays open when the text breaks the grammar.

## Project rules

- **Reference edition for the UI:** the Visual Studio (`../fsm-editor-vs`, C#) and JetBrains (`../fsm-editor-jb`, Kotlin) editions reimplement this one's UI, geometry and editing. A change to clipboard JSON or editor behavior needs the same change there. The file format, the grammar, validation, conversion, comparing and merging are not here: change them in `../fsm-cli` (the `.fsm` format, its reader, validator, grammar, code generation) or `../fsm-editor-common` (the layout file, the writer, conversion, comparing, merging, the interface), then `npm run build:common` and `npm run test:unit` here.
- **The writer** (fsm-editor-common's) is deterministic and lossless for what the editor can make. An editor feature that makes something the format can't hold gets refused by `stateOfModel` (`LostError`): prefer preventing it in the webview.
- **Text grammar:** behaviors (`entry`, `exit`, `do`, a transition's action) are argument-less calls separated by `;` (`a(); b()`). Guards, invariants and pre/postconditions are calls combined with `!`, `&&`, `||` and parentheses; `else` is allowed only on choice/junction branches. Triggers are event names or `after(<number><ms|s|m|h>)`. There are no variables, arguments, comparisons, dotted names or `when(...)`. The editor must refuse invalid text, and the validator must report it.
- **Deliberately out of scope:** state machine extension/inheritance (`{extended}`, redefinition) and the transition-oriented notation (send/receive signal symbols). Don't add them or list them as missing.
- **Submachines** reference another file by its path (`"submachine": "Payment.fsm"`), and connection point references name the points of that file by name.
- **Stereotypes** are plain names.
- **User-facing docs:** `README.md` (short guide), `docs/UML-CONFORMANCE.md` (supported features, file format, deviations, validation rules, execution semantics of generated code) and `docs/CODEGEN.md` (code generation from VS Code, the Trace Player's log format). The template language, the `fsm` command, the bundled templates, the code model and the semantics of the generated code are fsm-cli's, documented there (its README and `docs/CODEGEN.md`): CODEGEN.md links to them. Update the conformance doc when behavior or rules change.
- **fsm-cli is independent:** it knows nothing of this extension. A change made there for the editor's sake stays generic: nothing in fsm-cli (code, messages, templates, docs, tests) mentions or depends on the editor; this extension follows its format, schemas, test cases and messages.
