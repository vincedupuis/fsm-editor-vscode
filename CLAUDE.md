# FSM Editor

VS Code extension (desktop and web: vscode.dev, github.dev): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, "The .fsm file format", its schema and test cases); the layout file's is this extension's (`docs/UML-CONFORMANCE.md`, "The layout file", `schemas/fsm-layout.schema.json`, `test/unit/fixtures/layout`). Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when saved.

## Commands

```sh
npm install
npm run build:fsm          # fsm-cli (../fsm-cli) as WebAssembly, with its templates, schemas and test cases, into fsm/ (needs Rust + wasm32-unknown-unknown)
npm run compile            # tsc type-check (noEmit), then esbuild bundles
npm run watch              # esbuild watch
npm run test:unit          # unit and code generation tests (node:test, bundled by test/unit/run.mjs)
npm run test:web           # browser smoke test in VS Code for the Web (Chromium, headless)
npm run check:webview      # syntax-check media/editor.js
npm run package            # builds fsm-editor-<version>.vsix (vsce package --no-dependencies; release.yml runs it too)
```

`fsm/` (`fsm.wasm`, `templates/ts.jinja`, `templates/sml.jinja`, `schemas/*.schema.json`, `cases/`) is git-ignored: code generation, the text view's schemas, the tests and the VSIX need it (`cases/` isn't packaged). Run `npm run build:fsm` once, and again after changing `../fsm-cli`; it finds `cargo` on the PATH or in `~/.cargo/bin`. The workflows download it from the fsm-cli release pinned by `FSM_CLI_VERSION` in `release.yml` (`test-windows.yml` reads the pin from there), so that release must exist before this extension is released.

F5 launches an Extension Development Host on `examples/`. Automated tests:
- `npm run test:unit` (`test/unit/codegen.test.ts`): generates TypeScript through `fsm/fsm.wasm` with `ts.jinja` for the examples and for models built in code (`ModelBuilder` in `harness.ts`), bundles it with esbuild and runs it against recorded actions and a fake clock. Code model assertions go through a template that prints the code model as JSON (`codeModel()` in `harness.ts`). Add a case here for any change to code generation semantics (made in `../fsm-cli`).
- `npm run test:unit` (`test/unit/sml.test.ts`): generates C++ with `sml.jinja` for the examples and for a model of every feature, compiles it (`-Wall -Wextra -Wpedantic -Werror`) with a driver that records the calls (`cpp.ts`), and runs the same scenarios as the TypeScript tests. Needs a C++17 compiler (`CXX`, or `c++`/`clang++`/`g++`) and Boost.SML: `SML_INCLUDE`, or downloaded once into `node_modules/.cache`; skipped without them, but failed when `CI` is set (GitHub Actions sets it). CI compiles it with GCC, so check GCC too when changing the template (e.g. in a `gcc` container).
- `npm run test:unit` (`test/unit/compare.test.ts`, `merge.test.ts`): the comparison and the merge logic.
- `npm run test:unit` (`test/unit/layout.test.ts`): the layout schema and the layout reader agree on `test/unit/fixtures/layout` (`valid/`, `invalid/`) and the examples' layout files (the schema checked with `ajv`). Change the schema, the reader, the fixtures and the conformance doc's "The layout file" together.
- `npm run test:unit` (`test/unit/format.test.ts`, `cases.test.ts`, `xmi.test.ts`): the format (write-read-write gives the same bytes, relative positions, the examples), the reader and validator against fsm-cli's test cases (`fsm/cases`: the same problems, lines and ids), converting old files.
- `npm run test:web` (`test/web/index.ts`): opens copies of the examples in VS Code for the Web and checks activation, validation diagnostics at their lines, following a text edit, its save and its text closed unsaved, submachine resolution, opening an old or conflicted file unchanged and converting an old file on save, code generation, the diagram diff and merge, a layout file renamed with its model file, and untitled machines.

Otherwise verify changes in the development host with the examples (`MediaPlayer.fsm`, and `Order.fsm`, which uses `Payment.fsm` as a submachine).

## Architecture

- Build: `esbuild.mjs` bundles `src/extension.ts` twice, into `out/extension.js` (Node, `main`) and `out/web/extension.js` (web worker, `browser`). Extension code must stay web-compatible: no Node modules, `Buffer` or `process`. Use `src/util.ts` for paths and text encoding, and `vscode.workspace.fs` for files. Only `src/trace/tail.ts` may use Node modules; the web build replaces it with `tail.web.ts` (esbuild plugin in `esbuild.mjs`).
- `src/extension.ts`: activation and commands (new machine, generate code, SVG and PNG export, open as text / as diagram, compare as diagrams). `activate` returns `sessionSummary()` for the browser test.
- Code generation (documented in `docs/CODEGEN.md`) is fsm-cli (`../fsm-cli`, Rust: validation, code model, Jinja templates), built as a WebAssembly module (`fsm/fsm.wasm`) that the extension runs on desktop and web alike. `src/fsmCli.ts` instantiates it with the standard `WebAssembly` API (no imports) and passes JSON: the texts of the `.fsm` files and of the template in, the files to write and the problems (`issues`, `error`) out; the request and response are described in fsm-cli's README ("WebAssembly"). The module reads no files: `src/codegenCommand.ts` reads the machine and the machines its submachine states reference, transitively (an open document's text when it is open), keyed by `/`-separated paths, then writes the files through `vscode.workspace.fs`. Templates are `.jinja` only; the module refuses `.hbs` with its own message, which the command shows as it is. The code model, the template language and the bundled templates are fsm-cli's.
- `src/fsmEditorProvider.ts`: `CustomEditorProvider` with its own document (`FsmDocument`), because one diagram edits two files: a document state holds the texts of the model and layout files and the webview's model JSON; each webview `edit` (model JSON) is written with `writeMachine` into a new state, fired as an undoable edit (VS Code's undo, redo, dirty mark, save, revert and hot-exit backups act on these states). An edit the format can't hold (`lost`) is refused. Saving writes both files (a layout file that couldn't be read is replaced only after asking); saving an old file converts the files linked to it too (`convertLinked`). Without changes of its own, a document follows its files on disk and the model file's text document. Read-only file systems (Git's) give a read-only diagram. The provider also lists the workspace's machines, resolves submachine paths, maps the Trace Player's ids to the diagram's (`derivedIds`), and publishes diagnostics at the lines the writer or reader gives.
- `src/model.ts`: `FsmModel`, a flat vertex list where `parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. Coordinates are absolute.
- `src/json.ts` + `src/format.ts`: the file format. The JSON reader and the model reader are fsm-cli's (`json.rs`, `format.rs`) ported: the same problems, messages, lines and derived ids. `format.ts` also reads and writes the layout file (relative positions, bend points relative to the innermost state containing both ends, automatic places for elements without an entry), writes both files deterministically (`writeMachine`: write(read(x)) = x), gives generated names (`assignNames`), and the ids fsm-cli gives a model's elements (`derivedIds`). A reference that names nothing is kept as `UNRESOLVED` + its text.
- `src/xmi.ts` + `src/xml.ts`: reading old files (XMI); `src/convert.ts` converts them, a group linked by submachines at a time. Nothing writes XMI.
- `src/load.ts`: a model from a file's text, either format (the Trace Player, code generation, summaries).
- `src/compare.ts` (matching by name, the changes and their properties, model and layout apart) and `src/merge.ts` (splitting conflict markers, `adopt`: taking one side's version of an element): no VS Code or webview API, as the C# and Kotlin editions will port them. `src/sessions.ts` links diagram panes: `DiffSession` (two panes, from **Compare as Diagrams**, since VS Code opens diffs of `.fsm` files as text diffs; nothing else is paired, so the sides are always known), `MergeSession` (the conflicted document as the result, its two sides served read-only by the `fsm-merge` file system, Git's common version through the Git extension when it is there). The webview shows a pane's role, marks and list (`diff` message) and sends `view`, `diffNav`, `diffLayout`, `mergeChoose`, `mergeAll`, `mergeComplete`.
- `src/validation.ts`: UML well-formedness rules, names and references, the text grammar and reachability, as `Issue[]` keyed by element id: fsm-cli's `validation.rs`, message for message.
- `media/editor.js` / `editor.css`: the whole diagram editor (toolbox, SVG canvas, properties panel, inline editing, SVG and PNG export). It's plain JavaScript without a build step or dependencies, and renders by rebuilding an SVG string. Its `cleanGroups` repeats `normalizeGroups` of `src/model.ts`, which the webview can't import. Its geometry is also ported to `Geometry.cs` (`../fsm-editor-vs`) and `Geometry.kt` (`../fsm-editor-jb`). Names ending with `*` are generated and not shown (`shown()`); name fields refuse spaces, `*` and `.` and names used elsewhere in the machine.
- `media/expressions.js`: the text grammar, a UMD module shared by the webview (`window.FsmExpressions`) and the validator (bundled by esbuild, typed by `expressions.d.ts`).

## Project rules

- **Reference edition:** the Visual Studio (`../fsm-editor-vs`, C#) and JetBrains (`../fsm-editor-jb`, Kotlin) editions reimplement this one (they still read and write XMI: the JSON format reaches them later). A change to the text grammar, validation rules or messages, the file format, clipboard JSON or editor behavior needs the same change there. The format's reference is `../fsm-cli` (reader, validator, schemas, test cases): change it there first, then here, and check here with `npm run build:fsm` and `npm run test:unit` (`cases.test.ts`). The validator runs twice, here (`src/validation.ts`, for the editor's diagnostics) and in `../fsm-cli` (before generating code): a change to its rules or messages goes to both. Code model and template changes are made in `../fsm-cli` only; run `npm run build:fsm` and `npm run test:unit` here after them.
- **The writer** must be deterministic and lossless for what the editor can make: `writeMachine(readMachine(x))` gives `x` back for any `x` it wrote (`format.test.ts`). An editor feature that makes something the format can't hold gets refused by `stateOfModel` (the `lost` list): prefer preventing it in the webview.
- **Text grammar:** behaviors (`entry`, `exit`, `do`, a transition's action) are argument-less calls separated by `;` (`a(); b()`). Guards, invariants and pre/postconditions are calls combined with `!`, `&&`, `||` and parentheses; `else` is allowed only on choice/junction branches. Triggers are event names or `after(<number><ms|s|m|h>)`. There are no variables, arguments, comparisons, dotted names or `when(...)`. The editor must refuse invalid text, and the validator must report it.
- **Deliberately out of scope:** state machine extension/inheritance (`{extended}`, redefinition) and the transition-oriented notation (send/receive signal symbols). Don't add them or list them as missing.
- **Submachines** reference another file by its path (`"submachine": "Payment.fsm"`), and connection point references name the points of that file by name.
- **Stereotypes** are plain names.
- **User-facing docs:** `README.md` (short guide), `docs/UML-CONFORMANCE.md` (supported features, file format, deviations, validation rules, execution semantics of generated code) and `docs/CODEGEN.md` (code generation from VS Code, the Trace Player's log format). The template language, the `fsm` command, the bundled templates, the code model and the semantics of the generated code are fsm-cli's, documented there (its README and `docs/CODEGEN.md`): CODEGEN.md links to them. Update the conformance doc when behavior or rules change.
- **fsm-cli is independent:** it knows nothing of this extension. A change made there for the editor's sake stays generic: nothing in fsm-cli (code, messages, templates, docs, tests) mentions or depends on the editor; this extension follows its format, schemas, test cases and messages.
